# Connection II Scenario Map

**Purpose:** enumerate every distinct end-to-end path an invoice can take through the Conformity workflow, intake to terminal outcome. This is the validation checklist Connection II works through one scenario at a time.

**Status:** read-only analysis, 2026-08-04 (first pass) and 2026-08-04 (second pass — decoding). Working copy: Conformity_CP1 (`{F542FB91-9563-4506-929F-BC279D1D5B37}`). No writes, no test objects created for either pass.

**Sources:** `WorkflowStates`/`WorkflowTransitions` tables in `provisioning.db` (live-queried for this pass, not from memory), the master 47-state behavior table in `progress.md`, and the four VAF apps' captured NVS configs in `rollback/2026-08-01_082750_conformity-write-protocol/`. Companion `.xlsx` version: `connection-ii-scenario-map.xlsx` (same 12 rows, color-coded by priority tier).

An Excel version of this table (`connection-ii-scenario-map.xlsx`, color-coded by priority tier) lives alongside this file.

## Headline findings from this pass (new, not previously written up)

1. **Every terminal branch of the workflow — Approval, Statement, OtherDoc, PackingSlip, AND Trash — binds its own Vault Toolbox action that cross-vault-moves the object into Approbation**, under a distinct destination class each. There is no purely-local terminal outcome except the housekeeping `Delete` that follows a successful Trash move. This means Connection II's handoff-completion blocker (item b) isn't unique to the happy path — every scenario below depends on it.
2. **Only `MoveToApproval` carries a destination `Workflow`+`WorkflowState`** (5 GUIDs total). `MoveToStatement`, `MoveToOtherDoc`, `MoveToPackingSLip`, and `To trash` carry only 3 destination GUIDs (Vault/Object type/Class) and no destination workflow placement.
3. **`WAIT_SQL_RETRY`'s retry-loop behavior is now directly confirmed for Conformity**, not just "plausible by analogy to v3.0" (the master table's prior framing). The `WORKFLOW_ERREUR`→`WAIT_SQL_RETRY` and `WAIT_SQL_RETRY`→`UPD_VendorID`/`UPD_SQL_CP1` edges carry a decoded VBScript timer guard (`DateDiff(...) > 1` minute since `Created`) — a genuine automatic retry, not a manual step.
4. **`RTE_Missing Value` (state 116) bypasses both the credit-check cascade and the entire duplicate-check cluster** on its way to `Control Invoices` — an invoice can reach Approbation without `FindDuplicates` ever running. Flagged as scenario #10, elevated for early validation given the risk.
5. **`SET_CREDIT_NEGATIF` is not a terminal branch** — it's a sign-flip step that always loops back through the duplicate-check cluster and a second `Control Invoices` classification pass (scenarios #8/#9).

## Decode findings (second pass, 2026-08-04)

Follow-up task: decode the classification/entry mechanisms flagged as undecoded gaps above, explicitly checking whether any of the four add-on apps (`ConformityVaultApplication`, `SQL Query Vault Application`, `M-Files Vault Toolbox`, `M-Files Property Calculator`) are bound to the relevant states by ID or alias reference — not just native VBScript. Method: full read of all four apps' captured NVS config JSON, cross-referenced against live-queried `WorkflowStates`/`WorkflowTransitions` in `provisioning.db`, plus a direct grep of all four config files for `"119"` and `Controlinvoices` (and `"115"`/`"143"`/`Newdocument` for the intake question) to rule out a missed reference rather than relying on read-through alone.

**1. `Control Invoices` (119) classification — confirmed manual, no automated driver anywhere.** State 119's own `GuardConditions` in the DB are fully empty (no VBScript, no property precondition). All 10 outgoing transitions (to 124/125/126/134/139/140/155/202/203/219) are unconditional/always-allowed except `119→125`, which carries a real but undecoded condition. A grep of all four apps' full config text for `"119"` and `Controlinvoices` returned zero matches — confirmed by direct search, not absence-of-evidence. **Nothing in this vault's captured configuration decides PO vs non-PO vs Statement vs OtherDoc vs PackingSlip vs CreditNegative vs UPD_To CP1.** A human/dashboard operator selects the destination transition manually; the entry-state preconditions on the chosen destination (124/202/203's VBScript field checks; 139/140's opaque native property condition) validate that the choice has complete-enough data — they do not perform the classification itself. This applies identically to the `119→219` (credit-note, scenario #8) and `119→134` (`UPD_To CP1`, scenario #12) edges — neither is app-driven either.

**2. Intake-landing quirk (test objects landing at 118 or 143 rather than 115) — confirmed real M-Files engine behavior, not a harness artifact and not an add-on redirect.** Grepped all four apps for `"115"`, `"143"`, and `Newdocument` — zero `ChangeWorkfow`-style (direct-assignment) bindings to either state, ruling out the same redirect pattern already confirmed elsewhere for `WORKFLOW_ERREUR`/`OUT_TO_UPD_CP1`. One new binding found: **M-Files Property Calculator does bind to state 115** (alias `WFS.Duplicate.Newdocument`, rule `Calculated_SubTotal` — computes `PD.Calculatedsub = Total-Tax1-Tax2`), but this is a pure calculation that never touches `State`, so it doesn't explain the quirk. The real explanation is already on record in `AUDIT_LOG.md`: object 5427, created with explicit `State=115`, auto-advanced one hop to 114 during the same checkin (`115→114`'s transition guard is unconditional) and then genuinely stopped there because 114's own progress depends on the SQL Query Vault Application's async call. Objects 5428/5429/5430, created with explicit `State=143` (deliberately bypassing 114), consistently cascaded through to 118 instead (`"143 doesn't stick"`, confirmed across 3 separate objects) — because 143's own branches and the downstream credit-check cascade (`216→211→213→212→219` and their fallback edges) are also unconditional, so M-Files auto-fires all of them in the same checkin until reaching 118, the first state whose forward progress genuinely depends on an async task (`FindDuplicates`, TaskType 3) rather than an immediately-evaluable condition. **Conclusion: on checkin, the engine auto-fires unconditional outgoing transitions repeatedly until it reaches a state that requires human action, a real conditional guard, or an async task result — real, repeatable behavior, not a bug in the test harness or a hidden add-on redirect.**

**3. Scenarios #4/#5 (Statement/OtherDoc) — guard confirmed native-only, plus a new finding.** Neither state 139 nor 140 is referenced by any of the four apps as a classification input; the opaque property-based precondition on each is confirmed to be a native M-Files declarative condition (not app-driven), though its raw byte encoding is still undecoded. **New:** `ConformityVaultApplication`'s `ChangeClassInWorkflow` reclassifies the local Conformity object to `CL.Trash` on entry to all three of `RTE_Statement`(139)/`Rte_OtherDoc`(140)/`RTE_PackingSlip`(203) — the same local reclassification already known for `Trash`(141) itself (`"Trash-Statement"`, `"Trash-OtherDoc"` ×2 entries, all `Enabled:true`). Statement/OtherDoc/PackingSlip are therefore treated identically to Trash on the Conformity side, even though the Vault Toolbox move sends each to a different destination class in Approbation.

**4. Scenario #8 credit-note sign-flip — exact per-field gate now confirmed.** `M-Files Property Calculator`'s `"Invoices (Crédit en Négatif)"` class has 5 separate rules, one per field (Total/Subtotal/Tax1/Tax2/Freight), **each independently gated** on `State = SET_CREDIT_NEGATIF AND that field > 0.00` — a field already zero or negative is left untouched. Property Calculator plays no role in the decision to route to 219 in the first place (see finding 1) — only in the sign-flip once it's entered.

**Methodology note — alias-derivation pattern, used only as a cross-check, not as sole evidence.** `WFS.<Workflow>.<Alias>` strings in these configs consistently squash to: state Name with spaces/underscores/hyphens/plus-signs stripped, first character kept, every other character lowercased (confirmed against 11 independent pairs already established in this project, e.g. `Rteapproval`=`RTE_Approval`/132, `Intoupdcp1`=`IN_TO_UPD_CP1`/195, `Checkcredit`=`Check_Credit`/211). **Not universal** — `WFS.Conformity.ToTrash` doesn't fit cleanly against any of the 47 known state Names, and `WFS.Conformity.Bratravendor` (Property Calculator's `Set__SubTotal` rule — labeled `"State = Set__SubTotal"` but bound to a different alias than that label) doesn't match any of the 47 states at all, likely a stale/orphaned binding. Neither was chased further — flagged for awareness, not acted on. **Existing attributions (e.g. `"To trash"` = state 141) were left unchanged given this ambiguity, not overridden on pattern-matching alone.**

Not chased in this pass (out of scope, flagged for awareness only): the orphaned-looking `Bratravendor` alias; the exact byte-level decode of the opaque Statement/OtherDoc preconditions and the `119→125` transition's own real condition; property MFilesId 1064/1039 (`Vendor`/`VendorID`, resolved by name only via original Conformity's persisted property table) written by SQL Query Vault Application's nested `UpdateVendor` sub-call — not classification-relevant.

## Deliberate simplification, stated explicitly

The SQL/CP1 vendor-learning-export sub-chain (`UPD_Learning = YES/NO` (120/121) → `UPD_SQL_CP1` (151) → `Fin_UPD_SQL_CP1` (152) → `UPD_CP1` (142) → `UPD_EXPORT_VENDORLIST` (136) → `WAIT_SYNCH_CSV` (144) → back to `Contrôle Apprentissage` (145) → `RTE_CP1_` (205) → `IN_TO_UPD_CP1` (195) → `OUT_TO_UPD_CP1` (196) → `UPD_To CP1` (134)) is treated as shared plumbing inside the #1/#2/#8/#9 backbone rather than its own scenario, since it always reconverges toward either `RTE_Duplicate2`/`Control_Before_Move` (the approval path) or `UPD_To CP1` (scenario #12). It has not been independently traced live end-to-end — the live-traced sub-path for #1/#2 used the `120→145` direct edge, not the `151`+ detour.

**Not a formal exhaustive graph enumeration.** Several states (118, 111, 119 in particular) are revisited by more than one sub-flow (e.g. the credit-negative loop re-enters 119), so a fully exhaustive path enumeration would be combinatorially larger than this list. This map is scoped to the business-relevant divergence points requested, plus the extensions found during this pass, at the granularity Connection II will actually test one scenario at a time.
