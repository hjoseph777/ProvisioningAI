Part One

What's already carrying the product

Worth saying plainly, because the findings below could read as harsher than the reality: this isn't a generic dashboard wearing a dark theme. Someone made real typographic and structural decisions here, and several of them are genuinely good.

A real typographic identity

JetBrains Mono for the working surface, Fraunces for the wordmark and headers — a deliberate technical/editorial pairing, not the Inter-everywhere default most internal tools ship with. It reads as built by someone who cared, on first glance, before any feature is even used.

The command palette is the real thing

⌘K opens a genuinely categorized search — sections, workflows, states — not a fuzzy-matched junk drawer. This is the single most "we sweat the details" moment in the product as it stands.

Roadmap placeholders don't look like placeholders

Discovery, Docs, and Copilot are unbuilt — and still ship a real icon, a one-sentence promise of what they'll do, and a milestone tag. Most products leave a grey box here. These read as "coming soon, deliberately," not "we forgot this page."

Process Docs has real visual craft

Correct BPMN color convention on Start/End, a live minimap, inline schema-validation status — this canvas alone would not look out of place in a funded design tool's marketing screenshots.

Part Two

The one thing worth fixing before anything else

If only one finding in this report gets acted on, it should be this one — everything else is a polish pass; this is a cohesion problem, and it's the difference between "one product with three tools" and "three tools that happen to share a login screen."

Studio, M-Files Flow, and Process Docs are the app's three real, working canvases — and each one currently commits to a different visual world. Studio and M-Files Flow render on a light, dotted-graph-paper background with flat blue rounded-rectangle nodes. Process Docs renders on a dark navy canvas with rounded-pill Start/End nodes, colored borders, and a completely different toolbar language (dropdown exports, a minimap, a validation status bar). Placed side by side, they don't read as one product's three modes — they read as three separate builds.

This isn't just an aesthetic nitpick. A user who's just gotten comfortable with M-Files Flow's zoom controls (a button row: −, +, Fit, lock) has to re-learn Process Docs' equivalent (a percentage readout plus separate dropdown menus), and re-learn it again for Studio's (a floating percentage badge plus a text "Recenter" button). Three tools, three sets of muscle memory, for the same underlying action.

Recommendation

Pick one canvas language and extend it to the other two — most of the engineering is already proven in Process Docs (the more recently built, more considered surface): its dark canvas, its toolbar pattern, its minimap. Studio and M-Files Flow's own interaction models (drag-to-connect, the editing palette, live translation) don't need to change — only the chrome around them does.

Part Three

Specific gaps, each cheap relative to its payoff

None of these are large builds. Each is the kind of thing that, left unfixed, quietly reads as "unfinished" to anyone evaluating the product seriously — and each is a matter of hours, not a redesign.

01
Polish

The JSON view has no syntax highlighting

It's a real, live, always-current view of the workflow — genuinely useful — rendered as a flat wall of one color. Every key, string, and boolean reads identically. A few lines of token-based coloring (keys in the accent blue, strings in the existing green, booleans in gold — the palette already exists elsewhere in the app) turns this from "a debug dump" into "a real inspector panel."

02
Polish

No visible save or sync state, anywhere

The workflow data is genuinely persisted (localStorage under the hood) — but nothing on screen ever confirms it. A user has to simply trust that their edits survived a reload. Tools at the bar this report is being held to (Linear, Notion, Figma) all show some version of "Saved" or a subtle sync pulse. Right now this product does the work and shows none of the receipt.

Recommendation

A small, quiet indicator near the workflow name — "Saved" with a checkmark, fading in after each change settles — closes a real trust gap for almost no visual cost.

03
Polish

A destructive action sits at the same visual weight as a status chip

The top bar's right side reads, left to right: a keyboard-shortcut hint (⌘K), a connection-status pill ("localhost"), and Reset — a destructive, workflow-clearing action — all styled as the same small pill button. Nothing about its appearance signals "this one is different from its neighbors."

Recommendation

Visually demote Reset relative to the passive chips beside it — an outline instead of a filled pill, or simply more spacing separating it from the status indicators it currently sits flush against — so a stray click doesn't read as equally safe as checking the connection.

04
Polish

Stats and Deliver both leave real vertical space unresolved

Six stat cards in a two-column grid, then several hundred pixels of empty canvas beneath them. The Deliver panel has the same shape: real content up top, dead space below. Neither is wrong — the content genuinely doesn't need more room — but next to the otherwise dense, purposeful rest of the app, both read as unfinished rather than intentionally spacious.

Recommendation

Constrain the panel's content to a natural height rather than a flex-filled column, or give each stat a second line of context (last-changed timestamp, a one-line trend) that earns the space it currently just leaves blank.

05
Polish

The command palette is missing its keyboard-hint footer

Every command palette this one is implicitly being compared to — Linear's, Raycast's, VS Code's — closes with a thin strip along the bottom: ↑↓ navigate, ↵ select, esc close. This one doesn't have it. It's a small, specific, instantly-recognizable signal of "we've shipped one of these before" — and it's currently the one piece missing from an otherwise well-executed feature.

06
Polish

"Available" and "roadmap" sections aren't visually distinguished consistently

Copilot's tab correctly shows a small lock glyph, signaling "not yet." Discovery and Docs — equally unbuilt, per their own placeholder screens — don't carry the same marker; they're only slightly dimmer text, a much subtler cue. The convention exists, it's just not applied to every tab it should cover.

Verdict

Where this actually stands

This is a genuinely distinctive internal tool, not a template with new labels — the typography was chosen on purpose, the command palette is built to a real standard, and the empty states show more care than most shipped products give their finished screens. That's the honest strength here, and it's worth protecting rather than smoothing over in a rewrite.

What separates it from "the best interface on GitHub" isn't ambition — it's cohesion. Three canvases built at three different moments now read as three different products, and a handful of small, specific signals (syntax color, a save indicator, a keyboard-hint footer) are the difference between "clearly cared for" and "clearly finished." None of it is a redesign. All of it is achievable without touching a single interaction that already works.
